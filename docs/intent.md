## 0. 最優先の制約（必ず守る）

1. **期限までに「動くもの」を必ず提出する。** 機能の多さより、いつ止めても提出できる状態を保つことを優先する。
2. **開発者は1人。** 管理しきれない数の spec・エージェント・hooks は作らない。
3. まずはできる限りシンプルに実装して、無駄なトークン消費やコストが発生しないようにする。
4. **AIなし・バックエンドなしで最後まで動く。** 静的サイトとしてブラウザで動作し、審査員が APIキーやインストールなしで試せること。
5. **判定はルール、AIは説明だけ。** ゲームの合否・攻撃の成否・雰囲気の急変判定はルールエンジンが決定論的に行う。
6. **`core/` は特定のアプリを知らない。** アプリの違いはシナリオJSON・ルール定義・テーマだけで表現する。
7. **安全ルール（`safety.md`）に反するものは作らない。** 詳細は 9章。
8. **フェーズとゲートを省略しない。** 構想 → 計画 → 構築の順に進め、計画承認（requirements → design → tasks の各段階で人が承認）と、Unit 完了時の検証ゲート（テスト通過後に人が動作を確認して承認）を必ず通す（10.2）。
9. ユーザーからの情報が足りない場合は質問する。

## 2. 作品のコンセプト

**作品名（仮）：Haunted Graph Kit**

**コアの1文：Place → Connect → Judge → Explain → Replay**
（ノードを置く → つなぐ → ルールで判定する → 説明する → 振り返る）

テキストや画像を 3D ノードとして自由に配置・変形・接続できる汎用エンジンを共通コアとし、そこから性質のまったく違う2つのアプリを作る。

| | アプリ1 | アプリ2 |
|---|---|---|
| 名前 | **スマホ屋敷のおばけ退治**（Ghost Mansion） | **Moodwalk**（ムードウォーク） |
| 利用者 | 中学生〜高校生 | 雰囲気を順番に設計するクリエイター |
| 性質 | 遊んで学ぶ（正解のあるゲーム） | 作って伝える（正解のない制作ツール） |
| 中心になるノード | テキストとアイコン | 画像 |
| コアの使われ方 | **守るため**（おばけ目線で弱点を見る） | **伝えるため**（来場者目線で体験を見る） |

審査で伝えたいこと：**同じ「配置・変形・接続・視点・ルール」の仕組みが、片方では安全、もう片方では表現という別の意味で使われている。**

## 3. 共通コア（`core/`）

### 3.1 モジュール

| モジュール | 役割 | 2つのアプリでの使われ方 |
|---|---|---|
| `Node` | 種類・位置・回転・大きさ・中身・メタデータ・**数値属性**（`Record<string, number>`）・**表と裏** | 部屋・ロボ・手紙・声／画像・テキスト・意図 |
| `Edge` | 向き・種類・ラベル。種類ごとに、自動の伝播を通すか止めるかをルール定義で決められる | 鍵（そのままの鍵・ベル付きの鍵）・被害が広がる道／意図と画像の結びつき・順路 |
| `Zone` | 空間を区切り、順序や階層を付ける。高低差と囲い（遮蔽）を持てる | フロア＝公開範囲（高低差と塀）／奥行きの区画＝体験の順番 |
| 詳細度表示 | ズームすると見える層 | 手紙の隠れ文字／主役画像の拡大 |
| `ViewPreset` | 視点の位置、見える範囲の絞り込み、経路に沿った移動 | おばけ目線／来場者目線のウォークスルー |
| `RuleEngine` | グラフの条件判定・経路探索・数値の集計。同じ入力なら必ず同じ結果 | 攻撃の成否と被害範囲／雰囲気の急変・同じ雰囲気の続きすぎ |
| 表示効果 | ルールの結果を見た目で表示。霧は Must（両アプリ共通）、発光などは Should | 出典のない答えに霧／急変区間に霧 |
| `Timeline` | 手順や状態の変化を順番に再生 | 事件の対処と被害の広がり／ウォークスルー再生 |
| `AIAdapter` | 解説用・画像解析用の差し替え口。**AIなしで動く代替実装を必ず持つ** | おばけ博士の解説（Could）／緊張感の推定（Could） |
| Scenario I/O | シナリオJSONの保存・読み込み・スキーマ検証（文言は `{ en, ja }` の構造） | ステージ定義／ボード定義 |
| Theme | ハロウィン調の見た目（霧・発光・ゴースト）を差し替え可能に | 屋敷テーマ／展示テーマ |

### 3.2 コアとアプリの境界
- **シナリオJSONとルール定義を差し替えるだけで済むものはアプリ側**に置く。
- アプリ固有の名前（おばけ、雰囲気カーブ等）を `core/` に書かない。
- 画像から明るさ・色の温度を計算する処理など、アプリ固有のデータ解析は `apps/` 側に置く。`core/` は数値属性（`Record<string, number>`）を受け取り、急変や連続の判定だけを行う。
- 「3つ目のアプリ」もJSONとルールの差し替えだけで作れることを、README（Should：`new-app-template`）で示す。
- `core/` は1つ。中は2層に分ける：`core/model`（Node・Edge・Zone・RuleEngine・Timeline・Scenario I/O。three.js に依存しない。PBT の対象）と `core/view`（3D表示・操作・視点・ウォークスルー）。
- 編集操作は `core/model` への命令として記録し、元に戻す／やり直すをコアで提供する。

### 3.3 3D操作の範囲
- 方針：操作の自由度を減らさず、操作の質（迷わない、戻せる、軽い）を守る。
- Must：ゾーン平面上のドラッグ移動とスナップ、gizmo による回転（3軸）と拡大縮小、2ノードを順にクリックして接続（エッジは自動追従）、元に戻す／やり直す、視点プリセットの切り替え、ウォークスルー。
- Should：複数選択、整列、キーボード操作。
- 対象外：物理演算、自由曲面、VR。
- 回転はどちらのアプリでもルールに意味を持たない（見た目のみ）。
- 11/13〜14 に最大1日のスパイクで「gizmo と視点操作が衝突しない」「スナップ」「エッジ追従」「画像50枚で 60fps」を確認する。通らなかった操作は代案に回し、decision-log.md に記録する。

## 4. アプリ1：スマホ屋敷のおばけ退治（`apps/ghost-mansion/`）

### 4.1 ねらい
- 安全なシステムやAIの使い方を知るだけでなく、**攻撃者がどんな意図でどこを狙うか**を理解し、**問題に直面したときに対処できる**ようになる。
- 生徒自身が、危ない屋敷を**直しながら学ぶ**（白紙からの自由制作はクリア後要素）。
- 専門用語は先に教えない。体験した後に「図鑑」で解禁する。

### 4.2 基本ループ「ロボの一日」：みほん → ととのえる → おばけの夜 → たいじする → ふりかえり

最初の画面は、**便利さは最大だが、ロボに鍵を渡しすぎた危険なプリセット屋敷**。生徒はこれを直していく、リファクタリング型のパズルとして遊ぶ。みほんからふりかえりまでを60〜90秒で1周できる構成にする（審査員が60秒で価値を体験できるようにするため）。

| ステップ | 生徒がやること | 学ぶこと |
|---|---|---|
| ① みほん | 「見本のうっかり屋敷」を、おばけとして攻略する。攻撃カードの前提条件が1つずつ満たされ、被害が広がるのを見る | 攻撃が成り立つ条件 |
| ② ととのえる | 自分の屋敷（プリセット）で、ロボに渡した鍵の種類を変える（そのままの鍵／ベル付きの鍵／線を切る）。おばけ目線の「弱点スキャナー」で、外から見える弱点を確かめる。ズームで、ロボが読む予定の手紙やページを調べる | 自分の持ち物とつながり、攻撃者から見える場所 |
| ③ おばけの夜 | Timeline で再生する侵入シミュレーション。ロボが決まった仕事を順にこなす。**ゲーム側が隠した**かくれ命令に従うと、鍵をたどって被害が広がる。ベル付きの鍵では伝播が止まる | 権限の大きさと被害の関係、人の確認の効果 |
| ④ たいじする | 被害が出たときだけ。同じ3Dグラフと Timeline の上で、3つの操作（ロボを止める、鍵の線を切る、大人・友達のノードへ相談の線をつなぐ）を行う | 困ったときの対処の順番 |
| ⑤ ふりかえり | 再生でどこで食い止められたかを見て、便利さと被害の2軸評価を確認。ととのえ直して再挑戦 | 便利さと安全さのバランス |

- 攻撃は生徒ではなくゲーム側から来る（自分で置いた手紙を自分で攻める形にはしない）。
- おばけになるのは①みほんだけ。②以降の自分の屋敷では、おばけ目線を「弱点スキャナー」と「侵入シミュレーション再生」として防御のために使う。
- 「見本のうっかり屋敷」は、プリセット屋敷の定義を、鍵をすべて渡した固定状態で使う導入専用の見本（別の屋敷は作らない）。
- 白紙からの自由制作はクリア後要素（Could）。

### 4.3 コアの機能に持たせる意味

| コアの機能 | ゲームでの意味 |
|---|---|
| 配置（Zone） | 同心円の4フロア＝公開範囲：🌐外の道（だれでも）→🏡庭（フレンド）→🛋️家の中（家族）→🔒金庫（自分だけ）。フロアごとに高低差を付け、境界に塀（遮蔽）を置く |
| 変形（大きさ） | ノードの大きさ＝大事さ（取られたときの被害の大きさ） |
| ズーム | 手紙の隠れ文字、写真の背景の手がかりが見える |
| 接続 | 線＝鍵や被害が広がる道。鍵には「そのままの鍵」と「ベル付きの鍵」がある。同じパスワードは「鎖」でつながる |
| 視点 | **俯瞰視点**では屋敷全体の配線が見える。**おばけ目線**（外の道からの低い視点）では塀の内側が隠れ、公開範囲に出ているノードと、外へ伸びる線だけが見える |
| 表と裏 | 声ノードを裏返すと作り物だと分かる |

- 3D にする理由：視点を変えると見えるものが変わること自体が学びになる（俯瞰では全体の配線、おばけ目線では外から見える弱点だけ）。見える範囲の判定は ViewPreset の絞り込み（ゾーンの公開範囲）でルールが決め、塀は見た目でそれを裏付ける。

### 4.4 AIセキュリティの中心：AIおてつだいロボ
- 生徒は屋敷に「AIおてつだいロボ」を置き、**どの部屋の鍵を渡すか**を線で決める。
- 鍵を渡すほど**便利ポイント**が増える（宿題・写真整理が早く終わる）。
- 鍵を渡すほど、ロボがだまされたときの**被害も大きくなる**。
- ロボに渡す鍵（Edge の種類）は3つから選ぶ。
  - **そのままの鍵**：自動で実行される。便利さは高い。だまされると被害がそのまま伝わる。
  - **ベル付きの鍵**：毎回、人が確認する（Human-in-the-Loop）。便利さは中。自動の攻撃による被害の伝播をここで止める。
  - **線を引かない**：便利さは増えないが、その先は安全。
- 評価は**便利さ（終わった仕事の数）と被害**を2軸の点で示し、⭐はその点の位置から表で決める。式は design.md で決める。鍵を全部外せば安全だが便利ポイントはゼロ。ちょうどよい渡し方を探すのがゲームの面白さ。
- **ゲーム内のロボはルールで動く。本物のLLMは使わない。**

### 4.5 AIに関わるおばけ（ステージ2「AIロボがやってきた」）

| おばけ | 中学生向けの場面 | 遊びの中での見え方 | 図鑑で解禁される用語 |
|---|---|---|---|
| 📜 かくれ命令おばけ | ロボに「このページをまとめて」と頼んだら、ページの中に「持ち主の写真を送れ」という小さな文字が隠れていた | 手紙ノードをズームすると隠れ文字が見える。ロボは見落とすが生徒は見つけられる | プロンプトインジェクション |
| 🗝️ 鍵ぬすみおばけ | だまされたロボが、鍵を持っている部屋に勝手に入る | ロボから出る線をたどって被害が広がる。鍵を減らすほど被害が小さくなる | 過剰な権限 |
| 👂 ききだしおばけ | AIチャットに話した住所や悩みが、思わぬところに残っている | AIに話した内容がノードとして外の道に流れ出す | 機密情報の入力・漏えい |
| 🎙️ ものまねおばけ | 家族の声そっくりの電話で「お金を送って」と言われる | 声ノードをおばけ目線で裏返すと作り物だと分かる（音声は作らず文字とアイコンで表現） | ディープフェイク／音声クローン |
| 🌫️ まことしやかおばけ | AIの答えをそのまま宿題に書いたら、うそが混じっていた | 答えノードを出典ノードにつながないと霧がかかる | ハルシネーション・誤情報 |

### 4.6 ステージ2の遊び方（60〜90秒で1周）
Must のおばけは2つ：「かくれ命令→鍵ぬすみ」の連鎖攻撃（1つの流れとして扱う）と、まことしやかおばけ（出典ノードにつながっていない答えに霧がかかる）。初級は連鎖攻撃のみ、中級は両方（4.8）。
1. **みほん**：「見本のうっかり屋敷」を、おばけとして攻略する。攻撃が成り立つ前提条件が1つずつ満たされ、被害が広がるのを見る。
2. **ととのえる**：プリセット屋敷はロボに「そのままの鍵」を渡しすぎている。鍵を「ベル付きの鍵」に変える、線を切る、で直す。便利ポイントと被害がどう動くかを見ながら調整する。おばけ目線の「弱点スキャナー」で外から見える弱点を確かめ、ロボが読む予定の手紙やページをズームで調べる。隠れ文字を見つけたら「読ませない」印を付けられる。
3. **おばけの夜**：ロボの仕事（ページの要約、写真の整理、メッセージへの返信）を順に再生する侵入シミュレーション。かくれ命令入りの手紙を読んだロボはだまされ、そのままの鍵をたどって部屋に入る（鍵ぬすみ）。ベル付きの鍵の先には届かない。中級では、ロボが作った宿題の答えが出典ノードにつながっていないと、答えに霧がかかる。
4. **たいじする**：被害が出たときだけ。事件「ロボがクラスのグループに変なメッセージを送った！」に対し、同じ3Dグラフと Timeline の上で3つの操作を行う：ロボを止める、鍵の線を切る、大人・友達のノードへ相談の線をつなぐ。順番は前後関係の条件だけで判定する（例：「ロボを止める」は「鍵の線を切る」より前）。別の2D画面は作らない。
5. **ふりかえり**：2軸評価と再生を見て、ととのえ直して再挑戦。

### 4.7 攻撃の表し方（攻撃カード）
攻撃は抽象化した「攻撃カード」でのみ表す。コード・コマンド・実際に使える文面は含めない。

```json
{
  "id": "hidden-command",
  "name": "かくれ命令",
  "attackerGoal": "ロボに本来の指示とは違う行動をとらせる",
  "motives": ["情報を盗みたい", "いたずら"],
  "targets": ["robot", "web-page", "message"],
  "preconditions": [
    { "label": "ロボが外の文章を読む", "check": { "edge": "reads", "from": "robot", "toZone": "outside" } },
    { "label": "ロボが鍵を持っている", "check": { "edge": "key", "from": "robot", "minCount": 1 } },
    { "label": "人の確認がない", "check": { "pathHasNoEdgeType": "bell-key", "from": "robot" } }
  ],
  "impact": "個人情報の漏えい、勝手な送信",
  "counters": ["鍵を減らす", "人が確認する", "外の文章と持ち主の指示を区別する"]
}
```

- 攻撃の成否は、生徒のグラフがカードの `preconditions` の `check` をすべて満たすかでルールエンジンが判定する。`label` は表示用。`check` の書式は design.md で確定する（上の例は仮）。
- どの前提条件を崩せば防げるかが見えることが、防御の理由の理解につながる。

### 4.8 難しさの調整
- 初級（中1〜）：部屋3〜4個、おばけ1体（かくれ命令→鍵ぬすみの連鎖）、対処操作3つ
- 中級：部屋を増やし、おばけ2体（連鎖攻撃＋まことしやかおばけ）
- 上級（高校生）：全おばけ、自分でおばけを作るモード（Could）

### 4.9 先生向けの裏づけ
5体のおばけのうち4体を、[OWASP Top 10 for LLM Applications (2025)](https://owasp.org/www-project-top-10-for-large-language-model-applications/assets/PDF/OWASP-Top-10-for-LLMs-v2025.pdf) の項目に対応させる。

| おばけ | OWASP (2025) |
|---|---|
| かくれ命令おばけ | LLM01: Prompt Injection |
| ききだしおばけ | LLM02: Sensitive Information Disclosure |
| 鍵ぬすみおばけ | LLM06: Excessive Agency |
| まことしやかおばけ | LLM09: Misinformation |

- ものまねおばけ（ディープフェイク／音声クローン）は OWASP LLM Top 10 の項目ではない。生成AI悪用リテラシーの項目として区別して書く。
- 2026年8月に新版が出たという二次情報がある（Excessive Agency が LLM03、Misinformation が LLM07 などに移動）。公式資料では未確認。提出前に公式資料で版と番号を確認し、出典（URLと確認日）を付ける。確認は reviewer エージェントが行う。

### 4.10 参考にした既存の考え方（ステージ1）
ステージ1「はじめてのスマホ」（つりおばけ、なりすましおばけ、のぞき見おばけ等）は構想済みだが、**今回の提出範囲はステージ2のみ**（Could 扱い）。

## 5. アプリ2：Moodwalk（`apps/moodwalk/`）

### 5.1 コンセプト
「見るムードボード」から「**歩いて体験するムードボード**」へ。
既存のボードは一度に全体を眺める一枚の絵だが、ゲーム・映像・展示・イベントで作り手が伝えたいのは、**順番に体験していく中で雰囲気がどう変わるか**である。

### 5.2 対象ユーザー
- ゲームのステージやシナリオを作る個人・小規模の開発者
- 映像や漫画の絵コンテ前のイメージを固める人
- 文化祭のお化け屋敷、展示、イベント空間を企画する人

### 5.3 既存ツールとの差別化
| ツール | 主な特徴 |
|---|---|
| Pinterest | 画像を見つける場（整理や作業の場ではない） |
| Milanote | 2Dの自由配置ボード（比較記事時点でAI支援なし） |
| PureRef | 参照画像をまとめて常に手前に表示するビューア |
| MoodFlow | AIによる作風・構図の分析、タグ付け、カラーパレット抽出、無限キャンバス |
| RenderAI Boards | 無限キャンバスで画像どうしを線でつなぐ |
| Moodzer／Lovart | 文章からAIがムードボード自体を生成 |

- 「AIで色やキーワードを抽出する」「画像を線でつなぐ」は既存機能であり、**差別化にしない**。
- 差別化の軸は「**順番（奥行き）**」「**体験（ウォークスルー）**」「**変化（雰囲気カーブ）**」「**方向性の説明（意図ノード）**」。
- ※各ツールの機能は提出前に最新情報を確認すること。

### 5.4 機能

| 機能 | 内容 | 既存ツールとの違い |
|---|---|---|
| 奥行き＝順路 | 3D空間の奥行きを「体験の順番」として使い、入口から出口へゾーンごとに並べる | 2Dのボードには順番の軸がない |
| ウォークスルー再生 | カメラが順路に沿って進み、来場者・プレイヤーの目線で体験できる | 一枚の絵ではなく体験として伝わる |
| 雰囲気カーブ | 各ゾーンの画像から明るさ・色の温度（・緊張感）を読み取り、順路に沿ったグラフにする | 抽出結果の一覧ではなく、時間とともにどう変化するかを見せる |
| 急変チェック | ルールエンジンが「急に明るくなる」「同じ雰囲気が長く続く」を検出し霧で知らせる。意図的な急変には印を付けられる | 配置の良し悪しを順番の観点で判断する |
| 意図ノード | 「なぜこの画像を選んだか」をテキストノードで書き、画像とつなぐ | 寄せ集めではなく方向性の説明になる |
| 出典の記録 | 画像ノードの裏に出典URLとメモを残す。AIで画像は生成しない | 生成型ツールとは役割を分ける |

### 5.5 雰囲気の読み取り方
- 明るさ・色の温度は**画像の色からルールで計算**する（AIなしで動く）。この計算（画像の読み込みとピクセル解析）は `apps/moodwalk/` 側に閉じ込める。`core/` には数値属性（`Record<string, number>`）として渡され、`core/` は急変・長く続くの判定だけを行う。
- 緊張感はAIで推定する（Could）。ユーザーが手で直せるようにする。
- 明るさ・色の温度の計算式は design.md で決める。急変・長く続くの判定しきい値（差の大きさ、ゾーン何個分か）はボードの設定として変えられるようにする。
- 画像はファイル選択とドラッグ＆ドロップで読み込む（CORS の制約を避けるため、URL 指定は出典の記録にだけ使う）。保存は IndexedDB と JSON の書き出し。

### 5.6 想定される価値（※仮説。ユーザー調査による裏づけはない）
- お化け屋敷なら「入口は静かに、中盤で一度ほっとさせ、出口直前で一番怖くする」という雰囲気の流れを、作る前にチームや先生と共有できる。
- 雰囲気カーブで「怖い場面が続きすぎて慣れてしまう」区間に気づける。
- 提出前に、文化祭の企画経験者などへの短い聞き取りで裏づけを取ることが望ましい。

### 5.7 デモ用サンプル
「文化祭のお化け屋敷の企画」ボードを1つ用意する。公開URLを開くと最初からこのボードが表示され、1回の操作でウォークスルー再生を始められるようにする（審査員が60秒で価値を体験できるように）。

## 9. 安全ルール（safety.md の元）

- 攻撃は抽象化した攻撃カードでのみ表す。**実際に使えるコード・コマンド・文面は書かない。**
- 手紙やページに隠す文字（かくれ命令）は、ゲーム内だけで通じる固定の短い文面にする。
- 教材は「見抜き方と防ぎ方」を扱い、攻撃の手順は教えない。
- ゲーム内のロボは本物のLLMで動かさない。
- 音声クローン・ディープフェイクを実際に作らない（文字とアイコンで表現）。
- 生徒の個人情報を収集しない。ログイン不要。
- 写真などのサンプル素材は架空・自作のものを使う。
- OWASP との対応や競合ツールの比較など、**主張には出典を付ける**（reviewer エージェントが確認）。OWASP は版を明記し（4.9）、ものまねおばけは OWASP の項目と区別して書く。
- Moodwalk で AI による画像生成は行わない。

## 10. 開発の進め方

### 10.1 ハイブリッド開発
- **Spec 駆動**：コア、ルール、データ構造、シナリオJSON、ゲームの判定ロジック
- **Vibe Coding**：3D表示の見た目、アニメーション、演出、UIの磨き込み
- Vibe に切り替えた後も、センサーと hooks は動かしたままにし、学習ループも続ける。センサーが通らない変更は採用しない。

### 10.2 開発フェーズの進め方

開発は「構想 → 計画 → 構築」の3フェーズを順に進め、「公開と学習」を構築と並行して回す。
各フェーズの終わりには、人が確認して承認する**ゲート**を置く。ゲートを通るまで次に進まない。

#### 全体像

| フェーズ | ステップ | 主な成果物 | ゲート |
|---|---|---|---|
| **① 構想**（目的と範囲を決める） | 意図の把握 → 実現性と制約の確認 → 範囲の確定 | intent.md、00-scope.md、safety.md | **範囲の確定**：intent.md の確定を decision-log.md に記録 |
| **② 計画**（仕様で設計する） | 要件分析 → アプリ設計（境界の設計） → Unit 分け → 進行計画 | 各 spec の requirements.md／design.md／tasks.md | **計画承認**：各ファイルを人が承認してから次へ |
| **③ 構築**（実装と検証を繰り返す） | 機能設計 → コード生成 → ビルドとテスト | コード、テスト、PBT | **検証ゲート**：センサーとテストがすべて通り、人が公開URLで動作を確認して承認したら次の Unit へ |
| **④ 公開と学習**（構築と並行） | デプロイ → 学びの反映 | 公開URL、lessons.md、steering の更新 | 毎日、提出できる状態であることを確認 |

#### ① 構想：目的と範囲を決める
- **意図の把握**：作品の狙い、2つのアプリの対象者と価値を確認する（2〜6章）。
- **実現性と制約の確認**：1人・約3週間・バックエンドなし・AIなしで動く、という制約の中で実現できるかを確認する（0章、8章）。
- **範囲の確定**：Must／Should／Could と、遅れたときの対処を決める（7章）。
- Kiro（architect エージェント）と対話し、intent.md の抜けや矛盾を指摘させてから確定する。
- この時点で、空のアプリ2つを公開する準備（spec `repo-foundation`）まで進め、**提出できる状態①**を作る。

#### ② 計画：仕様で設計する
- **要件分析**：requirements.md を EARS 形式で書く。中心になる要件は、3Dノードの配置、接続を伝わる影響（伝播）、視点の切り替え。
- **アプリ設計（境界の設計）**：design.md で、`core/` と `apps/` の境界となるインターフェースを定める。`core/` はグラフ計算・ルール判定・伝播・視点の切り替えを提供し、アプリはシナリオJSON・ルール定義・テーマ・視点の設定だけを渡す。表示（3D描画）と計算（グラフ・ルール）も分け、計算部分は描画なしでテストできるようにする。
- **Unit 分け**：準備のあと、開発を3つの Unit に分ける（下表）。
- **進行計画**：tasks.md を、数時間で終わる大きさのタスクに分ける。
- 各 spec は「何を作るか（requirements.md）」「正しさをどう判断するか（design.md の PBT の性質と検証条件）」「何を学んだか（lessons.md）」を分けて書く。

#### ③ 構築：実装と検証を繰り返す
- Unit 1 から順に、機能設計 → コード生成 → ビルドとテストを進める。
- hooks が保存時・タスク完了時にセンサーとテストを自動で実行する（10.3）。
- **検証ゲート**：センサーとテストがすべて通った後、人が公開URLで実際に動作を確認し、承認してから次の Unit に進む。承認は decision-log.md に「日付／Unit／確認したこと／結果」を1行で記録する。
- Unit 2・3 では、ルール・データは Spec 駆動、見た目は Vibe で進める（10.1）。

#### ④ 公開と学習：構築と並行して回す
- **公開**：GitHub Pages などにpush契機でデプロイし、いつでも提出できる状態を保つ。監視や障害対応などの本格的な運用は対象外とする。
- **学習の蓄積**：開発中に得た「Kiro への指示の直し方」「Kiro に守らせたいふるまい」「PBT で見つけた不具合」を lessons.md に記録する。繰り返し出てくるものは、steering のルールやセンサーに昇格させ、昇格したことを decision-log.md に記録する。

#### Unit とゲート

| Unit | 含む spec | 中身 | 検証ゲート（＝区切り） |
|---|---|---|---|
| 準備 | repo-foundation | ディレクトリ構成、センサー、空のアプリ2つ、公開設定 | 提出できる状態① |
| Unit 1：共通コア | core | グラフ計算、ノードの伝播、3D操作、視点の切り替え | コアのデモが動く |
| Unit 2：スマホ屋敷のおばけ退治 | app-ghost-mansion | 鍵（権限）の伝播、おばけ目線、被害の判定 | 提出できる状態② |
| Unit 3：Moodwalk | app-moodwalk | 奥行き＝順番の配置、来場者目線、雰囲気カーブの算出 | 提出できる状態③（最重要） |

#### 用語
- **Unit**：まとまって完成させる作業の単位（上表の Unit 1〜3。準備は Unit に数えない）。
- **タスク**：tasks.md の1項目。数時間で終わる大きさ。
- **計画承認**：requirements・design・tasks を人が承認すること。
- **検証ゲート**：Unit の完了時に、テストの通過と人による動作確認で承認すること。
- **学習ループ**：修正内容を記録し、繰り返すものをルールやセンサーに昇格させること。

### 10.3 センサー

| センサー | チェック内容 | タイミング |
|---|---|---|
| required-sections | requirements.md・design.md に必須見出し（PBT の性質、安全性など）があるか | spec の保存時 |
| type-check | `tsc --noEmit` | コードの保存時 |
| linter | lint | コードの保存時 |
| schema | シナリオJSONのスキーマ検証 | JSON の保存時 |

要件の抜け（旧 upstream-coverage・traceability）と出典の確認（旧 claim-sources）は、センサーにせず reviewer エージェントがゲート前に確認する。

重い処理（テスト・PBT）はタスク完了時のみ実行し、クレジット消費を抑える。

### 10.4 カスタムエージェント

| エージェント | 主に使うフェーズ | 役割 | 権限 |
|---|---|---|---|
| architect | ① 構想、② 計画 | intent.md の抜けや矛盾の指摘、Unit の分け方と design.md の作成。core/ がアプリに依存していないかを守る | 書き込み可 |
| reviewer | ② 計画、③ 構築 | 計画承認・検証ゲートの前に、design.md とコードを独立してレビュー。要件の抜け、PBT の性質とテストの抜け、safety.md 違反、主張の出典も確認する | **読み取りのみ** |

作る役とレビューする役を分け、レビュー役は読み取り専用にする。

### 10.5 skills
- `unit-approval`：Unit ごとに requirements → 承認 → design → 承認 → tasks → 承認 → 構築 → 検証ゲート を進める手順
- `submission-pack`：テスト件数、PBT で見つけた不具合、lessons を集めて提出用にまとめる

### 10.6 spec の分け方

| spec | 中身 | 完成の基準 |
|---|---|---|
| repo-foundation | ディレクトリ構成、センサーのスクリプト、空のアプリ2つ、公開設定 | 空のアプリ2つが公開URLで開ける |
| core | `core/model`（Node／Edge／Zone、Edge の種類ごとの伝播ルール、シナリオJSON、条件判定、経路探索、数値の集計、Timeline、元に戻す）と `core/view`（3D表示・操作、ゾーンの高低差と囲い、ズームで見える層、視点、ウォークスルー、霧）。画像解析など、アプリ固有の解析は含めない | PBT：保存→読み込みで内容が変わらない、エッジは存在するノードを指す、同じ入力なら同じ結果、エッジを取り除いても到達できるノードの集合は増えない、自動の伝播を止める種類のエッジの先には自動の伝播が届かない。2つの視点を切り替えるデモが動く |
| app-ghost-mansion | ステージ2（ロボの一日）、プリセット屋敷、見本屋敷、鍵の種類（そのまま／ベル付き）、連鎖攻撃、まことしやかおばけ、弱点スキャナー、3Dグラフ上の対処操作、2軸評価 | 導入からふりかえりまで60〜90秒で1周できる |
| app-moodwalk | ゾーン、画像の読み込みと明るさ・色の温度の計算（`apps/moodwalk/` 内）、雰囲気カーブ、急変チェック、意図ノード | 公開URLを開いて60秒以内に、サンプルのお化け屋敷を歩いて体験できる |
| new-app-template（Should） | 3つ目のアプリの作り方 | JSONとルールの差し替えだけで新アプリが動く |

requirements.md は EARS 形式（WHEN [条件] THE SYSTEM SHALL [動作]）で書く。

### 10.7 何を誰が作るか

| 対象 | 作り方 |
|---|---|
| intent.md、00-scope.md、safety.md | 人が書く（言い回しの調整のみ Kiro） |
| product.md、tech.md、structure.md | Kiro の Generate Steering Docs で生成し Refine、人が確認 |
| ディレクトリ構成、センサー | Kiro（spec `repo-foundation`）、各段階で人が承認 |
| hooks | Kiro（Ask Kiro to create a hook）、trigger とコマンドを人が確認 |
| カスタムエージェント、skills | Kiro が下書き、**権限は人が必ず確認** |
| lessons.md、decision-log.md | 空ファイルを作成し、hook と人が追記 |
